# Reproducing the paper's experiments

This guide explains how to rerun the experiments of

> Aina Toky Rasoamanana, Olivier Levillain, Hervé Debar. **Towards a Systematic and Automatic Use of State Machine
> Inference to Uncover Security Flaws and Fingerprint TLS Stacks.** ESORICS 2022, pp. 637–657.
> [hal-03997060](https://hal.science/hal-03997060)

with this test bed, both with the paper's learner (pylstar's **L\***, image `tls-test-bed/pylstar-tls`) and with
AALpy's **L#** (image `tls-test-bed/pylstar-tls-lsharp`). It also explains how to find, monitor, time and analyse the
results.

## 1. What the paper did

The paper infers the state machines of TLS clients and servers (Mealy machines: *message sent / messages received*)
with L\*, for 400+ versions of 9 TLS projects. It looks for deviations from the expected "happy paths" (authentication
bypasses, loops), reproduces known CVEs, finds new ones, and fingerprints stacks by their state machines.

| Id | Paper | What | Paper's result |
|---|---|---|---|
| E1 | §5, Table 1 | Inference time, OpenSSL 1.1.1k TLS 1.2 server | 6 states, **77 s** with all optimisations |
| E2 | §5 | Timing of a 1,400-inference campaign (30 in parallel) | mean ≈ 3 min, median 81 s, p10 27 s, p90 ≈ 8 min |
| E3 | §7.1, Fig. 4 | Server authentication bypasses in wolfSSL TLS 1.3 **clients** | CVE-2020-24613 (≤ 4.4), CVE-2021-3336 (≤ 4.6.0), CVE-2022-25638 (≤ 5.1.0) |
| E4 | §7.1, Fig. 5 | Client authentication bypass in wolfSSL TLS 1.3 **servers** | CVE-2022-25640 (≤ 5.1.x) |
| E5 | §7.1 | OpenSSL `s_client` "bypasses" | false positives; absent with curl+OpenSSL |
| E6 | §7.2, Table 2, App. B.1 | Loops before encryption (DoS) | Erlang 24, fizz, NSS 3.15–3.78, OpenSSL < 1.1.0, wolfSSL ≤ 4.4.0 (CVE-2020-12457), MatrixSSL 4.x (CVE-2022-25639); wolfSSL TLS 1.2 NoRenegotiation loop is a false positive |
| E7 | §7.3 | Unsolicited client authentication | several wolfSSL versions |
| E8 | App. B.2 | EarlyCCS (CVE-2014-0224), FREAK (CVE-2015-0204) | detected in old OpenSSL |
| E9 | App. B.3 | Bleichenbacher padding oracles | MatrixSSL ≤ 3.8.2, wolfSSL ≤ 3.12.2, Erlang 20.0 |
| E10 | §8.1, Table 3 | Fingerprinting TLS 1.3 servers | 13 classes, separated by 8 sequences |
| E11 | §7, App. A Table 4 | The whole corpus | 2,000+ state machines, up to 31 states |

The paper approximates equivalence queries with a **random walk**, then cross-checks the unique state machines with
**BDist** (distinguishing bound). The timeout is 1 s, raised to 3 s for stacks whose inference was unstable.

Three ready-made experiment lists cover all of this (section 4):

| File | Experiments | Lines |
|---|---|---|
| [`experiments/paper-table1.tsv`](../experiments/paper-table1.tsv) | E1 | 1 |
| [`experiments/paper-findings.tsv`](../experiments/paper-findings.tsv) | E3–E10, one line per result, each with the expected outcome | 56 |
| [`experiments/paper-full.tsv`](../experiments/paper-full.tsv) | E11 (and E2), the full Table 4 corpus | 3,836 |
| [`experiments/extra-stacks.tsv`](../experiments/extra-stacks.tsv) | BoringSSL, PicoTLS, patched mbedTLS (not in the paper) | 189 |

`paper-full.tsv` is generated by [`experiments/generate-paper-full.sh`](../experiments/generate-paper-full.sh) from
the version tags in `stacks/*/tags` and the version ranges of Table 4. It prints the number of versions per stack
family, to compare with Table 4.

## 2. Setting up

### Requirements
- Linux, or Windows with WSL 2 (run everything from the Linux side).
- Docker, `make`, `openssl`, `git`, and `flock` / `pkill` (util-linux / procps; present on standard distributions).
- Clone the repository on the Linux side. `.gitattributes` forces LF line endings; CRLF breaks the scripts.

### Crypto material and tools
```sh
make crypto-material                         # CAs, server and client certificates (crypto/material/)
make containers/tools/pylstar-tls.docker     # L* inference tool (pylstar-tls v0.3)
make containers/tools/pylstar-tls-lsharp.docker   # same tool, learning with AALpy's L#
make containers/tools/automaton2dot.docker   # graphs and analysis (pylstar-tls v0.5 scripts + Graphviz)
```

### Stack images
A stack version is a Docker image `tls-test-bed/<family>:<tag>`, built with
`make containers/<family>/<tag>.docker`, where `<tag>` is a file in `stacks/<stack dir>/tags/`:

| Family (image) | Stack directories | Build time / size (measured) |
|---|---|---|
| `openssl` | `openssl-git--0_9_8`, `openssl-git--1_0`, `openssl-git--1_1--3_0` | ~2 min, 0.25 GB |
| `curl-openssl` | `curl-openssl-git--1_1_1` (+ the matching `openssl` image) | ~3 min |
| `gnutls`, `curl-gnutls` | `gnutls-git`, `curl-gnutls-git` | ~26 min, 1.7 GB; +2 min |
| `mbedtls` | `mbedtls-git`, `mbedtls-vulnerable` | ~5 min, 1 GB |
| `wolfssl`, `curl-wolfssl` | `wolfssl-git`, `curl-wolfssl-git` | ~7 min, 3.2 GB; +28 min, 3.7 GB |
| `nss` | `nss-git--3_15` … `nss-git` | 3–7 min, 1.6 GB |
| `erlang` | `erlang-20-git`, `erlang-24-git` | ~9 min, 3.3 GB |
| `matrixssl` | `matrixssl-3.7.2` (`matrixssl-git` cannot be built, see §9) | ~1 min, 0.6 GB |
| `fizz` | `fizz-git` | ~17 min, 9 GB |

The times were measured on a 12-core machine. The full corpus is ~560 images, far more than a typical disk holds at
once, so use `run-experiments.sh --build --prune` (section 4), which builds each image when first needed and deletes
it once all its runs are done.

## 3. Running one inference by hand

```sh
./infer-server.sh   <image> <tls-version> <scenario> [pylstar-tls options]   # SUT = server
./infer-srv-auth.sh <image> <tls-version> <scenario> [pylstar-tls options]   # SUT = server requiring client certificates
./infer-client.sh   <image> <tls-version> <scenario> [pylstar-tls options]   # SUT = client
```

- `<image>`: e.g. `tls-test-bed/wolfssl:v4.4.0-stable`.
- `<tls-version>`: `1.0`, `1.2` or `1.3`, the version the SUT is configured with.
- `<scenario>`: the input vocabulary. Server inference (the tool plays the client) uses `scenarios/<s>-client.scenario`
  with `tls10`, `tls12`, `tls12simple`, `tls13` or `bb-oracle`. Client inference (the tool plays the server) uses
  `scenarios/<s>-server.scenario` with `tls10`, `tls12`, `tls13` or `freak`.
- **Options** (passed to pylstar-tls):

| Option | Meaning | Default |
|---|---|---|
| `-E RW:<steps>:<p>` | random-walk equivalence check: `<steps>` messages in total, restart with probability `<p>` after each | |
| `-E BDist:<n>` | distinguishing-bound check, all suffixes up to `<n>` messages (exhaustive; slow for large machines) | `BDist:3` |
| `-E WP:<n>` | Wp-method for at most `<n>` states (exponential) | |
| `--timeout <s>` | how long to wait for an answer before concluding "No RSP" | `1` |
| `--disable-happy-path-first` | don't try the scenario's expected paths first during equivalence checks | |
| `-v` | print every message sent and received | |
| `<msg> <msg> …` `[--loops N]` | **replay mode**: send this one sequence (N times) and print the answers, without learning | |

- **Environment variables:**
  - `INFERER_IMAGE=tls-test-bed/pylstar-tls-lsharp`: learn with L# (the default is L\*).
  - `RESULTS_DIR=<dir>`: where to write the results (default: `results/<kind>--<stack>--<scenario>--<inferer>--<time>-XXXXXX`).

Examples:
```sh
# L*, then L#, on the same server, with the paper's equivalence method
./infer-server.sh tls-test-bed/openssl:OpenSSL_1_1_1k 1.2 tls12 -E RW:10000:0.1
INFERER_IMAGE=tls-test-bed/pylstar-tls-lsharp ./infer-server.sh tls-test-bed/openssl:OpenSSL_1_1_1k 1.2 tls12 -E RW:10000:0.1

# wolfSSL 4.4.0 TLS 1.3 client
./infer-client.sh tls-test-bed/wolfssl:v4.4.0-stable 1.3 tls13 -E RW:10000:0.1

# wolfSSL 5.1.0 TLS 1.3 server requiring client authentication
./infer-srv-auth.sh tls-test-bed/wolfssl:v5.1.0-stable 1.3 tls13 -E RW:10000:0.1

# Replay one message sequence 20 times (checks a suspicious path, and determinism)
./infer-server.sh tls-test-bed/wolfssl:v5.2.0-stable 1.2 tls12 \
    TLS12ClientHelloRSA NoRenegotiation NoRenegotiation NoRenegotiation NoRenegotiation NoRenegotiation --loops 20
```

The input message names of a scenario are on its `input_vocabulary` line, and in the first line of any
`final.automaton` it produced.

## 4. Running many inferences: run-experiments.sh

[`run-experiments.sh`](../run-experiments.sh) runs lists of experiments, by default **with both L\* and L#**, records
the time of each run, and keeps going when a run fails.

```sh
./run-experiments.sh [options] <experiments.tsv>...
```

An experiments file has one experiment per line: `kind  image  tls_version  scenario  [pylstar-tls options]`, where
`kind` is `server`, `srv-auth` or `client`, and the `tls-test-bed/` prefix of the image is optional. Lines starting
with `#` are comments. For example:
```
server    openssl:OpenSSL_1_1_1k    1.2    tls12
client    wolfssl:v4.4.0-stable     1.3    tls13    --timeout 3
```

| Option | Meaning | Default |
|---|---|---|
| `--campaign NAME` | results go to `results/NAME/` | `campaign-<date>` |
| `--inferers LIST` | comma-separated inferers | `pylstar-tls,pylstar-tls-lsharp` (L\* and L#) |
| `--repeat R` | run each experiment R times | 1 |
| `--jobs N` | N inferences in parallel | 1 |
| `--eq METHOD` | equivalence method, used as `-E` unless the line has its own | `RW:10000:0.1` |
| `--max-time T` | stop a run after T (`3600`, `90m`, `4h`) | `4h` |
| `--build` | build missing images with `make` (once per image, even in parallel) | off |
| `--prune` | delete each stack image after its last run | off |
| `--skip-done` | skip runs that already have a `final.automaton` (resume an interrupted campaign) | off |
| `--dry-run` | print the runs and commands only | off |

Runs are grouped by stack image, so with `--prune` disk space is released as the campaign progresses. Duplicate lines
are run once. Every run's console output and timing are saved (section 6). When the campaign ends, summarize it with
`./summarize-results.sh results/NAME` (section 8).

Typical campaigns:
```sh
# E1: timing of Table 1, sequential, 5 repetitions per learner
./run-experiments.sh --campaign table1 --repeat 5 --jobs 1 experiments/paper-table1.tsv

# E3-E10: every result of the paper
./run-experiments.sh --campaign findings --build --jobs 8 experiments/paper-findings.tsv

# E11 (and E2): the whole corpus, as in the paper (30 in parallel), building and pruning images on the fly
./run-experiments.sh --campaign full --build --prune --jobs 30 --max-time 2h experiments/paper-full.tsv

# Only one stack family of the corpus (any line filter works)
grep -P '\twolfssl:' experiments/paper-full.tsv > /tmp/wolfssl.tsv
./run-experiments.sh --campaign wolfssl --build --prune --jobs 8 /tmp/wolfssl.tsv
```

Interrupting a campaign (Ctrl-C) stops the runner. Leftover containers can be removed with
`docker ps -q --filter name=tls- | xargs -r docker kill`, and the campaign resumed with the same command plus
`--skip-done`.

## 5. The experiments, one by one

Each subsection gives the commands, the paper's result, and what to look for. "Graph" means
`./automaton2dot.sh <result folder>` (section 8.1); "security results" is the line it prints, also found in
`findings.csv`.

### E1. Inference time (Table 1)
```sh
./run-experiments.sh --campaign table1 --repeat 5 --jobs 1 experiments/paper-table1.tsv
./summarize-results.sh results/table1
```
- **Paper:** OpenSSL 1.1.1k TLS 1.2 server, 6 states, 77 s on average with all optimisations on a 16-core EPYC 7302P.
- **Check:** `analysis/runs.csv` gives `states` (expect 6) and `total_time_s` / `wall_s` per run. `analysis/timing.csv`
  gives the mean and median per learner.
- Run it on an otherwise idle machine; see section 7.3.
- Only the "all optimisations" cell of Table 1 can be reproduced (section 9).

### E2. Campaign timing statistics (§5)
- **Paper:** 1,400 inferences, 30 in parallel, about 2.5 h; mean ≈ 3 min, median 81 s, p10 27 s, p90 ≈ 8 min.
- **Reproduce:** run E11 with `--jobs 30`, then read `analysis/timing.csv` (`metric = total_time_s`, columns
  `mean`, `median`, `p10`, `p90`) for each learner. The campaign's elapsed time is between the first and last lines
  of `results/full/runner.log`.

### E3. wolfSSL TLS 1.3 clients: server authentication bypasses (Fig. 4)
In `paper-findings.tsv`: `client wolfssl:<version> 1.3 tls13` for 4.4.0, 4.5.0, 4.6.0, 5.1.0, 5.2.0, plus
`curl-wolfssl` versions. Expected:

| Version | Expected path to ApplicationData without proper server authentication | CVE |
|---|---|---|
| ≤ 4.4.0 | ServerHello, EncryptedExtensions, Certificate, **Finished** (no CertificateVerify) → client sends Finished+AppData | CVE-2020-24613 |
| 4.5.0–4.6.0 | ServerHello, EE, **EmptyCertificate, CertificateVerify** (signed with any key) → AppData | CVE-2021-3336 |
| ≤ 5.1.0 | ServerHello, EE, **EmptyCertificate, invalid CertificateVerify** → AppData | CVE-2022-25638 |
| 5.2.0 | none: only Cert + valid CV leads to Finished+AppData | fixed |

- **Check:** security results show `Possible authentication bypass`, and the graph shows the bypass path in red (the
  `Fin / Fin+AppData` transition reachable without `CV`). The same paths appear for `curl-wolfssl`, which uses a real
  client (the paper used it to confirm the bypasses).
- **Confirm by replay:** send the path to the client and check that it answers with application data, e.g. for
  4.4.0:
  ```sh
  ./infer-client.sh tls-test-bed/wolfssl:v4.4.0-stable 1.3 tls13 \
      TLS13ServerHello TLS13EncryptedExtensions TLS13Certificate_valid TLSFinished TLSApplicationData
  ```
  The exact input names are on the first line of the run's `final.automaton`.

### E4. wolfSSL TLS 1.3 servers: client authentication bypass (Fig. 5)
`srv-auth wolfssl:<version> 1.3 tls13` for 4.4.0, 5.1.0, 5.2.0.
- **Expect up to 5.1.x:** ClientHello, [Certificate,] **Finished** without CertificateVerify is accepted and
  ApplicationData is answered (CVE-2022-25640). Untrusted and empty certificates are correctly rejected.
- **Expect in 5.2.0:** fixed.
- **Check:** security results `Possible authentication bypass` (the analysis uses the `server.tls13-auth` rules for
  `srv-auth` runs).

### E5. OpenSSL s_client "bypasses" are false positives
`client openssl:<version> 1.3 tls13` vs `client curl-openssl:<version> 1.3 tls13`.
- **Expect:** the `openssl` (s_client) state machines accept untrusted or invalid certificates, because s_client only
  warns. The curl+OpenSSL machines do not.
- **Lesson:** security results on `openssl:` client images are not vulnerabilities; use the `curl-*` images to judge
  client certificate checks.

### E6. Loops before encryption (Table 2, App. B.1)

| Lines in `paper-findings.tsv` | Expected loop (on which message) |
|---|---|
| `server erlang:OTP-24.2.1 1.2 tls12` / `1.0 tls10` | NoRenegotiation alert or ApplicationData, before the handshake completes |
| `client fizz:v2021.06.14.00 1.3 tls13` (and 2021.02) | ChangeCipherSpec |
| `server nss:NSS_3_15_5_RTM` / `NSS_3_78_RTM 1.2 tls12` | NoRenegotiation alert |
| `server openssl:OpenSSL_1_0_2u 1.2 tls12` (vs `OpenSSL_1_1_1k`) | empty ApplicationData (absent in 1.1.1k) |
| `server wolfssl:v4.4.0-stable 1.2 tls12` (vs `v4.5.0`) | CVE-2020-12457 (fixed in 4.5.0) |
| `server wolfssl:v5.2.0-stable 1.2 tls12` | NoRenegotiation self-loop on the initial state: **false positive** |

- **Check:** security results show `Pre-[...] loops found`, and the graph has orange self-loops in the states before
  ChangeCipherSpec (or ClientHello for TLS 1.3).
- **Confirm** as the paper did: repeat the loop message many times in replay mode and check that the connection stays
  open. The wolfSSL TLS 1.2 NoRenegotiation loop closes after 4 warnings, which shows L\*'s model is only an
  approximation of behaviour deep in the state machine.
  ```sh
  ./infer-server.sh tls-test-bed/wolfssl:v5.2.0-stable 1.2 tls12 TLS12ClientHelloRSA \
      NoRenegotiation NoRenegotiation NoRenegotiation NoRenegotiation NoRenegotiation NoRenegotiation
  ```
  The paper also kept connections open for hours by sending one message per minute; replay mode sends as fast as
  possible, so that part needs a custom script.
- MatrixSSL 4.0–4.3 (CVE-2022-25639) cannot be reproduced (section 9).

### E7. Unsolicited client authentication (§7.3)
`server wolfssl:<version> 1.3 tls13` (no client authentication requested).
- **Expect:** some wolfSSL versions accept Certificate / CertificateVerify that the server never asked for.
- **Check:** in the graph, non-grey transitions on `Cert` / `CV` after ClientHello. The automatic security checks do
  not flag this, so look at the graph.

### E8. EarlyCCS and FREAK in OpenSSL (App. B.2)
- **EarlyCCS (CVE-2014-0224):** `server openssl:` 0.9.8za vs 0.9.8zb, 1.0.0l vs 1.0.0m (`1.0 tls10`), 1.0.1h vs
  1.0.1i (`1.2 tls12`). Expect `ChangeCipherSpec` accepted before ClientKeyExchange in the vulnerable versions, and an
  alert/EOF in the fixed ones.
- **FREAK (CVE-2015-0204):** `client openssl:` 0.9.8zc vs 0.9.8zd, 1.0.0o vs 1.0.0p, 1.0.1j vs 1.0.1k with the
  `freak` scenario (`1.0`). Expect vulnerable clients to continue the handshake after an RSA EXPORT ServerHello and
  ServerKeyExchange.
- **Check:** compare each pair's graphs, or `diff` their `final.automaton` files. The difference is the bug. `freak`
  graphs are drawn without colours (pylstar-tls has no colouring rules for it).

### E9. Bleichenbacher padding oracles (App. B.3)
`server <image> 1.0 bb-oracle` for wolfSSL 3.12.2 (vs 3.13.0), Erlang OTP-20.0 and MatrixSSL 3.7.2.
- **Expect** in vulnerable stacks: a state where `TLS12CKE_ok` and malformed ClientKeyExchange messages
  (`TLS12CKE_wrong_tls_version`, `TLS12CKE_0002_modified`, …) give different answers.
- **Check:** security results `Possible BB oracle`.

### E10. Fingerprinting TLS 1.3 servers (Table 3)
The `E10` lines of `paper-findings.tsv` (one version per class), or every TLS 1.3 server of `paper-full.tsv`.

| Class (paper) | States |
|---|---|
| Erlang 24.0.3–24.2.1 | 9 |
| GnuTLS 3.6.16–3.7.2 | 4 |
| MatrixSSL 4.0.0–4.1.0 / 4.2.1–4.3.0 | 4 / 6 (not reproducible here) |
| NSS 3.39–3.40 / 3.41–3.78 | 4 / 4 |
| OpenSSL 1.1.1a–1.1.1n / 3.0.0–3.0.2 | 4 / 4 |
| wolfSSL 3.15.5–4.0.0 / 4.1.0–4.6.0 / 4.7.0–4.8.1 / 5.0.0–5.1.1 | 7 each |
| wolfSSL 5.2.0 | 6 |

- **Check:**
  - `analysis/classes-server-v1.3-tls13.csv` groups runs with identical state machines; compare its classes and state
    counts with the table above.
  - `analysis/distinguishers-server-v1.3-tls13.txt` lists the input sequences that separate the classes. The paper
    needs 8 for 13 classes; expect a similar number for the 11 classes reproducible here.
  - With the full corpus, also check that **each class's version range** matches Table 3.

### E11. The whole corpus (Table 4)
```sh
experiments/generate-paper-full.sh     # (re)generates paper-full.tsv, prints versions per family
./run-experiments.sh --campaign full --build --prune --jobs 30 --max-time 2h experiments/paper-full.tsv
./summarize-results.sh results/full
```
- **Paper:** over 2,000 state machines with up to 31 states.
- **Check:** `runs.csv` (states column; status counts in the summary output), `findings.csv` (all potential issues),
  `classes-*.csv` per scenario, and `failed.tsv` (rerun those with `--timeout 3`, section 8.5).
- `paper-full.tsv` is a superset of what the paper ran: it pairs every version with every applicable scenario,
  including `bb-oracle` for all TLS 1.0 servers and `freak` for all TLS 1.0 clients. Filter it if time is short.

## 6. Where the results are

Each inference writes one folder. With `run-experiments.sh` it is
`results/<campaign>/<kind>--<stack>--<scenario>--v<tls>[--<options>]--<inferer>--r<repeat>/`, for example
`results/findings/client--wolfssl_v4.4.0-stable--tls13--v1.3--pylstar-tls-lsharp--r1/`. With the `infer-*.sh` scripts
it is `results/<kind>--<stack>--<scenario>--<inferer>--<time>-XXXXXX/` (or `$RESULTS_DIR`).

| File | Content |
|---|---|
| `final.automaton` | **The inferred state machine.** Line 1: the input alphabet. Then one transition per line: `from_state, to_state, message_sent, response`. State 0 is a fresh connection; several received messages are joined with `+`. Special responses: `No RSP` (nothing within the timeout), `EOF` (connection closed), `FatalAlert(x)` / `Warning(x)` |
| `N.automaton` | the hypothesis of learning round N (same format) |
| `N.stats` | counters when hypothesis N was submitted to the equivalence check |
| `N.counterexample` | written when hypothesis N was refuted: the counterexample sequence, then the counters |
| `final.stats` | counters at convergence (`Inference converged`) |
| `infer_server.log` / `infer_client.log` | settings (alphabet, equivalence method, timeout) and final summary; written at the end |
| `console.log` | (`run-experiments.sh`) everything printed, including live progress and, for L#, `L# learning rounds: R, learning time: Ls, equivalence query time: Es` |
| `run.tsv` | (`run-experiments.sh`) the command, start/end time, **wall time**, exit status (`ok`, `failed`, `timeout`), load average, `--jobs` |
| `final.dot`, `final.svg` | (`automaton2dot.sh`) the graph |

Counters in the `*.stats` files:
- `time spent so far`: seconds since learning started.
- `n_states`: states of the hypothesis.
- `n_queries` / `n_letters`: message sequences / messages the learner asked about.
- `n_submitted_queries` / `n_submitted_letters`: those actually sent to the SUT (**one submitted query is one TLS
  connection**). The rest were answered from the cache.

Campaign-level files: `results/<campaign>/runner.log` (one `START` / `END` line per run, with status and wall time;
`BUILD` / `PRUNE` lines) and `results/<campaign>/analysis/` (section 8).

## 7. Monitoring and timing (L\* vs L#)

### 7.1 Watching a campaign live
```sh
tail -f results/<campaign>/runner.log                       # runs starting and ending, with status and wall time
tail -f results/<campaign>/<run>/console.log                # one run's progress (hypotheses, counterexamples)
ls -lt results/<campaign>/<run>/                            # a new N.stats appears at each learning round
cat results/<campaign>/<run>/N.stats                        # time and queries so far
docker ps --filter name=tls-                                # running SUT and inference containers
docker stats --no-stream                                    # their CPU and memory use
./summarize-results.sh results/<campaign> --no-bdist        # any time: tables so far, unfinished runs with elapsed time
```
A run with no new `N.stats` for a long time is in a long equivalence check. Equivalence checks print nothing until
they finish; `BDist` on large state machines can take hours (see 7.3).

### 7.2 Where each time measurement comes from
For every run, `summarize-results.sh` reports (in `analysis/runs.csv`):

| Column | Source | Meaning |
|---|---|---|
| `wall_s` | `run.tsv` | whole run, including container start-up and teardown |
| `total_time_s` | `final.stats` | learning + equivalence checks |
| `equivalence_time_s` | sum of `N.stats` → `N.counterexample` / `final.stats` intervals | time in equivalence checks |
| `learning_time_s` | `total_time_s − equivalence_time_s` | time building hypotheses (membership queries) |
| `lsharp_learning_s`, `lsharp_equivalence_s`, `lsharp_rounds` | `console.log` | AALpy's own split, for L# runs (should agree with the two above) |
| `n_submitted_queries`, `n_submitted_letters` | `final.stats` | TLS connections and messages actually sent |

The learning/equivalence split is computed the same way for both learners, so it can be compared directly.

Without the runner, take the same numbers by hand: `time` the command (wall time), and read `time spent so far` and
the counters in `final.stats`, `N.stats` and `N.counterexample`.

### 7.3 Comparing L\* and L# fairly
- **Same settings:** run both learners on the same image, scenario, `-E` method and `--timeout`.
  `run-experiments.sh` does this by default.
- **Primary metric: TLS connections and messages sent** (`n_submitted_queries`, `n_submitted_letters`). They don't
  depend on machine load. Wall time does: the same 60,025-connection OpenSSL inference has been measured at 57 s and
  at 1,259 s on the same machine, depending on load.
- **Timing runs sequentially:** for timing comparisons use `--jobs 1 --repeat 3` (or more) on an idle machine, and
  compare medians. Coverage campaigns (E11) can run in parallel; `run.tsv` records `jobs` and the load average, so
  loaded runs can be identified.
- **Random walks are random:** with `RW`, each run explores differently, hence the repeats. `BDist` is
  deterministic, but much more expensive.
- **Example** (this repo, `RW:10000:0.1`, two inferences in parallel): the OpenSSL 1.1.1k TLS 1.2 server (E1) gave the
  same 6-state machine with both learners. L\* used 1,980 connections, 121 s learning + 10 s equivalence checking;
  L# used 956 connections, 25 s + 14 s.
- **Read the split, not just the total:**
  - L# usually needs far fewer queries to *learn* (another test here: 176 connections and 34 s, against 3,004 and
    515 s for L\*).
  - The equivalence check then runs on a cold cache: pylstar-tls skips the 1 s "No RSP" wait only for prefixes it has
    already seen, and L\*'s heavier learning phase leaves more of them cached.
  - With `BDist:3`, that made L#'s *total* slower in one client test (38.8 vs 16.6 min) despite cheaper learning.
  - `compare.csv` shows both phases, so this effect is visible per experiment.
- **Same model:** check that L\* and L# learned the same model (`same_model` column). They should whenever the
  equivalence check is good enough; a difference means one of them stopped on an incomplete hypothesis.

## 8. Analysing the results

```sh
./summarize-results.sh results/<campaign>              # add --no-bdist to skip the distinguishing bound (faster)
```
It prints a short summary and writes `results/<campaign>/analysis/`:

| File | Content |
|---|---|
| `runs.csv` | one row per run: identity, status, states, rounds, model hash, BDist, all timings and counters, `working`, `security_results` |
| `compare.csv` | one row per L\*/L# pair: `same_model`, states, and L\*, L# and ratio (L#/L\*) columns for connections, messages, learning time, equivalence time, total time, wall time |
| `timing.csv` | per learner and metric: count, mean, median, p10, p90, total (the paper's §5 statistics) |
| `classes-<kind>-v<tls>-<scenario>.csv` | identical state machines grouped: class, states, hash, member stacks |
| `distinguishers-<kind>-v<tls>-<scenario>.txt` | input sequences that separate those classes (fingerprints) |
| `findings.csv` | runs with security results, or whose handshake doesn't work |
| `failed.tsv` | failed or timed-out runs, with `--timeout 3` added, ready to rerun |

It can be pointed at any folder, including `results/` itself (all campaigns at once) or folders made by hand with
`infer-*.sh`.

### 8.1 Graphs
```sh
./automaton2dot.sh results/<campaign>/<run>              # writes final.dot and final.svg in that folder
./automaton2dot.sh <file.automaton> server.tls12         # any automaton, with an explicit scenario
```
This uses pylstar-tls's `automaton2dot.py`:
- messages are abbreviated (`CH` = ClientHello, `SH` = ServerHello, `CV` = CertificateVerify, `Fin`, `AppData`, …);
- transitions with the same destination and answer are merged (`*` = every other input);
- **green** marks the expected handshake (happy path), **grey** expected errors leading to the closed state, and
  **red / orange** paths flagged by the security checks (authentication bypass / loops);
- it prints the model hash, whether the handshake works, the number of states, the distinguishing bound, and the
  security results.

The paper's reading rule (§6) is that anything neither green nor grey deviates from the RFC and deserves a look.

### 8.2 Findings
- `findings.csv` lists runs with `Possible authentication bypass`, `Pre-[...] loops found` or `Possible BB oracle`,
  and runs where `working` is False (no complete handshake: often a broken image or a scenario the stack doesn't
  support).
- Compare it with section 5's expectations, then **confirm** each finding by replay (E3, E6). An inferred state
  machine is only an approximation: the paper confirmed every finding before calling it a vulnerability, and found
  false positives (E5, E6).

### 8.3 Classes and fingerprints
- Runs with the same model hash have identical state machines. `classes-*.csv` groups them per kind / TLS version /
  scenario. L\* and L# runs of one stack land in the same class when they learned the same model.
- **Table 3:** look at `classes-server-v1.3-tls13.csv`.
- **Version ranges:** the corpus shows where a project's behaviour changes between consecutive versions.
- `distinguishers-*.txt` gives the sequences that tell the classes apart. Replaying them against an unknown server and
  matching its answers identifies its class, which is the paper's fingerprinting (§8).

### 8.4 Cross-checking with BDist (as in the paper)
Random walks can miss behaviour. For each class (one representative per class is enough):
1. Read its distinguishing bound: the `bdist` column of `runs.csv`, or
   `docker run --rm -v "$PWD/results":/r tls-test-bed/automaton2dot sh -c 'cd /opt/pylstar-tls-v0.5/src && python compute_distinguishing_bound.py /r/<campaign>/<run>/final.automaton'`.
2. Rerun that stack with `-E BDist:<bound>` (one line in a new experiments file, e.g. with `--inferers pylstar-tls`).
3. Check that the model hash is unchanged.

BDist's cost grows with *states × inputs^bound*: a 26-state, 14-input wolfSSL TLS 1.2 server needs about 2 million
queries at `BDist:3`, which is hours to days.

### 8.5 Failed and unstable runs
- `status=failed` with `Incompatible path found` in `console.log` means the stack answered the same sequence
  differently twice. The paper's remedy is a longer timeout: rerun `analysis/failed.tsv`, which adds `--timeout 3`:
  ```sh
  ./run-experiments.sh --campaign full-retry --build --prune --jobs 30 results/full/analysis/failed.tsv
  ```
- `status=timeout`: the run exceeded `--max-time` (usually a long equivalence check). These runs are in `failed.tsv`
  too, but a longer `--timeout` won't help them: rerun them with a cheaper `-E` or a longer `--max-time`.
- `status=build-failed`: see `results/<campaign>/.runner/build-<image>.log`.
- **Determinism check:** rerun a sample with `--repeat 2` and compare model hashes (same class in `classes-*.csv`).

## 9. Known differences from the paper

- **MatrixSSL 4.0–4.3 cannot be built.** Its source repository (github.com/matrixssl/matrixssl) no longer exists. This
  removes CVE-2022-25639 (E6) and two Table 3 classes (E10). Their lines are commented out in `paper-full.tsv`.
  MatrixSSL 3.7.2 is unaffected.
- **Scenarios:** pylstar-tls v0.3's scenarios can differ slightly from the paper's (e.g. `tls12` has 14 inputs here;
  the paper's Table 1 experiment used 12), so state counts and times may differ a little.
- **Table 1:** only the "all optimisations on" cell (77 s) can be reproduced. pylstar-tls always applies its
  optimisations (EOF-is-final, skipping timeouts on known answers), and statelearner (2,945 s) is not included.
- **Random-walk parameters:** the paper doesn't give them. `RW:10000:0.1` (10,000 messages, average walk ~10 messages)
  is this repo's default; change it with `--eq`.
- **fizz:** Table 2 mentions a `22.01.24` fizz snapshot; only the 2021.02–2021.06 snapshots (App. A) are in the tags.
- **wolfSSL:** `paper-full.tsv` has 21 versions in 3.15.5–5.2.0, while the paper reports 20. One of the
  letter-suffixed tags (`3.15.5a`, `4.2.0c`, `4.7.1r`) was presumably not used.
- **OpenSSL 1.0.1d** is excluded, as in the paper (defective CBC implementation).
- **Hardware:** the paper used a 16-core AMD EPYC 7302P with 128 GB of RAM, running 30 inferences in parallel. Expect
  different absolute times.
- **Package sources:** several images build on Debian releases that are end-of-life (stretch, buster, bullseye); their
  package sources point to archive.debian.org.
