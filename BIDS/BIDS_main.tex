\section{Project Summary} 

\subsection{Top Level Research Project Description}
Cryptographic protocols are fundamental to secure distributed communications across the world, yet informal design practices and unexpressed assumptions often leave protocols open to attack. As such, protocols must undergo rigorous testing and verification to ensure that they remain secure in all circumstances. This research investigates methods to improve cryptographic protocol verification by comparing Cryptographic Protocol Shapes Analyzer (CPSA) and s(CASP), focusing on each framework's ability to detect protocol vulnerabilities that the other overlooks. While CPSA analyzes protocols by characterizing all possible execution shapes, s(CASP) utilizes goal oriented constraint answer set programming to provide verifiable, step by step traces of protocol execution paths. By benchmarking each framework's ability to identify both documented and novel protocol vulnerabilities, this work will assess their respective capabilities, trade offs, and limitations. In addition to this verification, this research will also explore whether active automata learning can expose vulnerabilities that static methods miss. If we treat an algorithm as a black box, we can use the $L^*$ algorithm to learn and construct an equivalent representation of the algorithm through carefully created input queries and their observed outputs. By probing the learned model, we will determine if CPSA and s(CASP) missed any vulnerabilities or attack vectors.\\

\subsection{Terminology}
\begin{itemize}
    \item \textbf{Cryptographic Protocol}: A distributed algorithm that describes precisely the interactions between two or more entities in service of agreed security objectives \cite{toorani2016securityprotocolsnutshell}.
    \item \textbf{Answer Set Programming (ASP)}: A modeling language that states a computational problem in terms of constraints over a binary domain \cite{10.1145/2043174.2043195}.
    \item \textbf{Atom}: An elementary proposition that makes up a literal \cite{10.1145/2043174.2043195}.
    \item \textbf{Literal}: An atom or its negation \cite{10.1145/2043174.2043195}.
    \item \textbf{Rule}: A justification of the form $a \leftarrow b_1,\dots, b_m, not\ c_1,\dots,not\ c_n$, where the head $a$ is derived by a body of literals that all resolve to true \cite{10.1145/2043174.2043195}.
    \item \textbf{Program}: A finite collection of rules \cite{10.1145/2043174.2043195}.
    \item \textbf{Fact}: A rule with no body, i.e., no preconditions, and is therefore established directly \cite{10.1145/2043174.2043195}.
    \item \textbf{Answer Set}: The formalization of a rule's intuition as exactly the derivations of each sub-rule within it \cite{10.1145/2043174.2043195}.
    \item \textbf{Grounded Program}: A program containing no variables \cite{10.1145/2043174.2043195}.
    \item \textbf{Grounding}: The process by which variables and recursive rule invocations are removed from a program \cite{10.1145/2043174.2043195}.
    \item \textbf{s(ASP)}: A goal-directed, predicate-level form of ASP that circumvents grounding entirely, avoiding exponential growth in program size \cite{Marple2017TheS}.
    \item \textbf{s(CASP)}: An extension of s(ASP) to variables over continuous domains, treating them as constraints on the answer rather than requiring grounding and resolution \cite{ARIAS_CARRO_SALAZAR_MARPLE_GUPTA_2018}.
    \item \textbf{Backward-Chaining}: The query process of s(CASP) in which evaluation begins at the goal and works backwards through rule heads to their bodies, generating subgoals until the proof chain terminates at facts \cite{Arias_2020}.
    \item \textbf{Trace}: The record of the backward-chaining process that makes s(CASP) explainable \cite{Arias_2020}.
    \item \textbf{CPSA (Cryptographic Protocol Shapes Analyzer)}: A tool that attempts to enumerate all unique executions, or shapes, of a protocol that are possible.
    \item \textbf{Shape}: A unique, possible execution of a cryptographic protocol, as enumerated by CPSA.
    \item \textbf{Dolev-Yao Model}: A model of network communication granting the adversary complete control over messages sent between principals, within which CPSA enumerates protocol shapes \cite{1056650}.
    \item \textbf{Formal Verification}: The use of tools and techniques to mathematically verify the security properties of a cryptographic protocol specification against a well-defined set of assumptions.
    \item \textbf{Strand}: A sequence of events representing either an execution by a legitimate party or a sequence of a perpetrator's actions \cite{doi:10.3233/JCS-1999-72-304}.
    \item \textbf{Burrows-Abadi-Needham (BAN) Logic}: A belief logic that analyzes an information exchange protocol by determining whether the information it trades is trustworthy, protected against eavesdropping, or both \cite{10.1145/77648.77649}.
    \item \textbf{Model Checking}: One of the two techniques, alongside theorem proving, that dominate the formal verification of security protocols \cite{pourpouneh}.
    \item \textbf{Theorem Proving}: The verification technique, complementary to model checking, that derives a protocol's correctness from a deduction system \cite{pourpouneh}.
    \item \textbf{Regular Language}: The class of languages that Angluin's $L^*$ algorithm is capable of learning \cite{angluin1987}.
    \item \textbf{Minimally Adequate Teacher (MAT)}: An oracle, assumed by $L^*$, capable of answering membership and equivalence queries about an unknown regular language \cite{angluin1987}.
    \item \textbf{Membership Query}: A query to the Minimally Adequate Teacher asking whether a given string belongs to the unknown target language \cite{angluin1987}.
    \item \textbf{Equivalence Query}: A query to the Minimally Adequate Teacher asking whether a hypothesized language equals the unknown target language, returning a counterexample when it does not \cite{angluin1987}.
    \item \textbf{$L^*$ Algorithm}: An algorithm, introduced by Angluin, that identifies an unknown regular set using only membership and equivalence queries to a Minimally Adequate Teacher \cite{angluin1987}.
    \item \textbf{Deterministic Finite Automaton (DFA)}: The model of computation that de Ruiter observed typically underlies the implementation of security protocols \cite{deruiter2015}.
    \item \textbf{Active Automata Learning}: The class of techniques, exemplified by $L^*$, that infer an automaton describing a black-box system's behavior through targeted queries \cite{deruiter2015}.
\end{itemize}

\section{Executive Summary}

As day-to-day life becomes more intertwined with technology, there is a growing need to secure information. Cryptographic protocols are fundamental for information security, but formally analyzing their security remains a challenging and computationally intensive problem. This project focuses on investigating complementary approaches for analyzing cryptographic protocols, with CPSA (Cryptographic Protocol Shapes Analyzer) serving as our primary reference tool. 

We will first analyze and formally verify a cryptographic protocol to outline its vulnerabilities using CPSA. We will also investigate the possibility of using Artificial Intelligence to make this process more efficient. We will then utilize s(CASP), which is an extension of s(ASP), to see if we can replicate the same flaws discovered by CPSA. This would allow us to find another potential tool to give us better deterministic results compared to CPSA.

We will also investigate the use of machine learning algorithms to analyze cryptographic protocols as black-box systems. A learning algorithm uses membership and equivalence queries to construct a model of the target protocol and determine whether the learned model can reproduce the same behavior as the original protocol. If this is possible, it can be used as an attack surface to expose the vulnerabilities of a given protocol. Additionally, if the learned model exactly mimics the original, we can also investigate whether there are certain counterexamples that are not discovered through formal verification. 

\section{Motivation}
\label{sec:mot}
Prior to the advent, rise, and situation of information technology, keeping a secret was as simple as turning away from the temptation of gossip. Then, a message was as secure as the strength of the message holder's will against persuasion. In this new data era, the security of information is a critical task. A cryptographic protocol is a distributed algorithm that describes precisely the interactions between two or more entities in service of agreed security objectives \cite{toorani2016securityprotocolsnutshell}, and these are essential in the security of messages traveling across the globe today. 

The rapid maturation of new technologies and techniques makes imperative the guarantee that the protocols that exist are correct and sound. However, the design of protocols is slow and when deployed their security guarantees are often limited. Thus, research on developing tools and techniques to accelerate the pace of formally verifying protocols is quite active. Recently, investigating the applicability of AI into the domain of cybersecurity, broadly, is in-vogue; an example of this being found in \cite{10.1007/978-3-031-87496-3_10}. However, the use of artificial intelligence (AI), particularly in the form of large language models (LLMs) is not to taken lightly for its proclivity for hallucinations \cite{Ji_2023,churilov2026rangeshrinksthreatremains,Huang_2025,10.1093/jla/laae003}; in fact, it has been shown that the problem of hallucinations is not fixable \cite{kalai2025languagemodelshallucinate}. However, we can still use AI reliably, as will be shown in ~\ref{subsec:asp}. In light of this, we are motivated by not only the analysis and formal verification of protocols, but also by exploring the use of a deterministic, explainable AI in this usage case. 

In the same vein of using existing tools in a fresh capacity, it is of great curiosity to us the applicability of learning algorithms. Section~\ref{sec:learnalgo} deals with learning algorithms and their place in this work in greater detail. In short, we wish to determine whether or not treating a cryptographic protocol as a black-box will lead an initially ``blank'' algorithm learning the protocol—which we define as being able to be a copy, however exact, of the protocol by treating it as a regular language. This not only presents a new attack vector but also substantiates the findings of CPSA if we are able to replicate the same behavior in this learned copy. And, if we are able to find that the learned copy exactly mimics the original, another avenue for investigation is in whethere there are certain counterexamples the former experiences that are not present in the latter. 


\section{Previous Work}
\subsection{ASP, s(ASP), and s(CASP)}
\label{subsec:asp}
Answer Set Programming (ASP) is a modeling language that states a computational problem in terms of constraints over a binary domain \cite{10.1145/2043174.2043195}. Answer set programs begin with \textit{atoms}, which are elementary propositions that make up \textit{literals}, which are the atoms themselves and their negations. Together, they form \textit{rules} that are justifications. They are of the form $$a \leftarrow b_1,\dots, b_m, not \text{ } c_1,\dots,not \text{ } c_n$$ where we say the \textit{head} $a$ is \textit{derived} by a \textit{body} of literals $b_1,\dots, b_m, not \text{ } c_1,\dots,not \text{ } c_n$ that all resolve to true. Incidentally, \cite{10.1145/2043174.2043195} offers an enlightening example, where the rule $$light\_on \leftarrow power\_on, not \text{ } broken$$ is taken to mean that $light\_on$  resolves to true once it has been established that the power is on and the light itself is not \text{ } broken.  \textit{Programs} are finite collections of rules. 

As it stands, the simple program of $power\_on$ stands to reason and makes sense, but a closer analysis realizes that the $not \text{ }$ operator indicates a modality is not \text{ } deliverable \cite{10.1145/2043174.2043195}. Hence, $power\_on$ is a \textit{fact} that should be derived but $broken$ should not \text{ } as it is a state. The intuition of these rules is best formalized by \textit{Answer Sets} that are exactly derivations of each ``sub-rule'' of a rule. Again, \cite{10.1145/2043174.2043195} offers anot \text{ }her good example for the general rule of having a $high\_salary$, where
\begin{equation*}
    \begin{align*}
        high\_salary \leftarrow employed, educated \\
        educated \leftarrow high\_salary\\
        employed \leftarrow motivated\\
        motivated.
    \end{align*}
\end{equation*}
We regard \textit{motivated} is \textit{established} as it is the head of a rule that has no body—no \textit{preconditions}.

The rules shown above have no variables, hence we say the program is \textit{grounded}. The intent of the grounding process is that the variables and the links, the recursive invocation of rules within other rules, are removed. Taking from the previous example, we can reform it to demonstrate the program for ascertaining a $high\_salary$ for an employee $X$, where
\begin{equation*}
    \begin{align*}
        high\_salary(X) \leftarrow employed(X), educated(X) \\
        educated(X) \leftarrow high\_salary(X)\\
        employed(X) \leftarrow motivated(X)\\
        motivated(Joe).
    \end{align*}
\end{equation*}
Of note, $X$ is treated as a variable and the fact that $Joe$ is motivated is what has been established. This means that all four atoms are tired to that single person $Joe$ via $X$. There are some stipulations on the constructions of rules, which are expounded in \cite{ARIAS_CARRO_SALAZAR_MARPLE_GUPTA_2018}.

The expressivity of ASP makes it attractive to the development of intelligent applications. However, it was observed in \cite{Marple2017TheS} that there are eight shortcomings of ASP that propelled a shift to goal-directed, predicate-level ASP (s(ASP)). This move allowed for grounding to be circumvented entirely, which in turn dodged an exponential growth of program size. \cite{ARIAS_CARRO_SALAZAR_MARPLE_GUPTA_2018} is an implementation of s(ASP) with a constraint solver. Similar to how Prolog was extended by Constraint Logic Programming, s(CASP) extended ASP to variables over continuous domains where they are treated as \textit{constraints} on the answer itself instead of the program having to ground, and ultimately resolve, the variables as they were observed. 

\cite{Arias_2020} added that s(CASP) is more explainable, and this comes from a process called \textit{backwards-chaining}. When s(CASP) is queried, the program begins at the goal and works backwards through the rule heads to their bodies. The body literals become a new subgoal and this process repeats until the proof chain capitulates at the facts. The \textit{trace} of this is what makes s(CASP) so explainable. We refer the reader to \cite{Arias_2020} for more. 

A careful study of ASP and its successors forms one of the linchpins of this project. The CPSA attempts to enumerate all the unique executions, \textit{shapes}, of a protocol which are possible. Since the protocols examined by CPSA carry a finitely many number of shapes, analysis is made simpler. One prong of our work is to propose using s(CASP) in a capacity in which it has not been found. Since the number of shapes in a cryptographic protocol are small in number, we will consider in this project implementing a protocol as an answer set program since the risk of a combinatorial explosion on account of grounding is low. Since the proof trace generated by s(CASP) is to some extent similar to the rote enumeration method employed by CPSA, we endeavor to examine whether or not s(CASP) can perform a task similarly to CPSA. In other words, we intend to incorporate to some level a deterministic artificial intelligence into the formal analysis and verification of a cryptographic protocol. 


\subsection{The CPSA Algorithm}
Given a cryptographic protocol, the Cryptographic Protocol Shapes Analyzer (CPSA) enumerates all the unique executions such protocol which are possible, called the protocol's \textit{shapes}, within a pure Dolev-Yao model \cite{1056650}. In order to ascertain the shapes, CPSA begins with some initial behavior of the protocol that it then uses to discover the protocol's compatible shapes \cite{10.1007/978-3-031-87496-3_10}. CPSA is complete—i.e., it will eventually discover every shape for a protocol (though, not all) \cite{1056650}. We refer the reader to Section~\ref{subsec:asp}, where we have already expounded on the use of CPSA as it relates to this project, particularly as a baseline against the use of s(CASP). 


\subsection{Cryptographic Protocol Analysis and Verification pre-AI}
Before ``AI" as it is understood today set ablaze the interest of researchers in automating, broadly, work, cryptographic protocols were formally approached by hand. Two techniques currently dominate the formal verification of security protocols: model checking and theorem proving \cite{pourpouneh}. That began with the work of \cite{10.1145/77648.77649}, whose Burrows–Abadi–Needham (BAN) logic postulates helped to define and analyze information exchange protocols by determining whether or not the information they trade in is (a) trustworthy, (b) protected against eavesdropping, or (c) both. While rigorous, BAN logic can only analyze a finite number of sessions that can be generated. Furthermore, BAN, belief, logics cannot deal with security flaws from an interleaving of protocol steps and cannot elucidate any properties of protocols beyond authentication \cite{torlak2006knowledgeflowanalysissecurity}. Using strand spaces, introduced by \cite{353594.353603}, and upon which CPSA is based, a graph-based model was introduced that allowed for proving the authentication and security properties of a protocol directly from the message structure without belief logic and without restricting to finite-state systems. Indeed, this strand space model is more expressive than BAN logic alone. As it stands, Scyther is used for model checking and deduction systems for theorem proving, and either was done following BAN logic \cite{pourpouneh}.



\subsection{Previous Attempts at Using AI in Cryptographic Protocol Analysis and Verification}
\label{sec:aiprotocol}
\cite{ohno2023securityverificationframeworkcryptographic} noted that the problem with formal verification as a tool for cryptographic protocol analysis is that it requires a large amount of computational time and does not guarantee decidability and proposes a machine learning technique to guarantee the verification time is linear. To do this, the authors first had to address the dearth of suitable data, in the form of protocol data accompanied by security labels, which they did by advancing a way to create arbitrarily large datasets by automatically generating random protocols and assigning security labels to them
using formal verification tools \cite{ohno2023securityverificationframeworkcryptographic}. The authors go further as to construct a neural network that processes a protocol along with its structural features, series and tree structures. Lastly, they evaluate their technique by testing it on practical cryptographic protocols, which is a sort of testbench we can leverage in our own project. 

LLMs have also been sighted, and cited, in the field, which started in the work of \cite{curaba2024cryptoformalevalintegratingllmsformal}. There, the authors introduced a benchmark to assess the ability of LLMs to autonomously identify vulnerabilities in new cryptographic protocols through interaction with Tamarin \cite{curaba2024cryptoformalevalintegratingllmsformal}. Their work also includes a dataset of flawed communication protocols and a method for automatically verifying the vulnerabilities stated by the LLMs (again, another useful tool for our present work). In fact, another \textit{potential} extension of our work could be to observe if LLMs are able to demonstrate improvements from the results in \cite{curaba2024cryptoformalevalintegratingllmsformal}, which is as of the writing herein two years passed). 


\subsection{On Learning Algorithms}
\label{sec:learnalgo}
In 1987, Dana Angluin unveiled $L^*$, an algorithm invented to learn a regular language \cite{angluin1987}. The invention rests on there being what is called a Minimally Adequate Teacher (MAT) capable of answering queries of two types: (1) membership queries (i.e., ``is this a part of you?'') and (2) equivalence queries (``is that the same as you, and if not, give me a telling counterexample''). Angluin's central contribution is that $L^*$ was able to identify an unknown regular set purely by asking about what is and is not a member, those two queries aforementioned.
	It was best observed by de Ruiter that the implementation of security protocols often entails an implementation of deterministic finite-state automata (DFAs) \cite{deruiter2015}, which gives rise to a simple flow: if we are able to trace through the DFA from head to tail, we will observe that the protocol, better put rather as its implementation, succeeded, and that it failed otherwise. Algorithms for state machine inference present an open opportunity to further apply active automata learning to the verification and analysis of security protocols, as was done by \cite{deruiter2015} on TLS (a.k.a., Transport Layer Security).


 
\section{Project Goals}
The ultimate goal of this project is to analyze a cryptographic protocol by formally verifying its security properties and bring such results to publication. Without belaboring this subject further, we state plainly our goals in a list below. 

\begin{itemize}
    \item Use CPSA to analyze and formally verify a cryptographic protocol;
    \item implement such protocol as an answer set and employ s(CASP) to the task of verifying the security properties of a protocol using queries; 
    \item treat the cryptographic protocol as a black-box and run an automata learning algorithm $L^*$ against it to see if (a) the protocol can actually be learned and (b) having learned the protocol, if its copy can replicate the same errors and gaps and potentially tease out new ones.

\subsection{Research Project Plan \& Approach}

The research plan is divided into 3 prongs. The following describes the prongs in greater detail. 
\begin{itemize}
    \item Analysis and Formal Verification of Cryptographic Protocol(s). Formal verification using CSPA will be conducted on at least one cryptographic protocol to identify unsoundness. \end{itemize}

\subsection{The Protocol Under Study: TLS 1.3}
\label{subsec:tls13}
We chose Transport Layer Security (TLS) 1.3 \cite{rfc8446} as the protocol for this project. TLS is the protocol that secures the vast majority of traffic on the Internet, and it is one of the two protocols the problem description names as underlying agentic AI systems such as the Model Context Protocol. TLS 1.3 comes in two modes:
\begin{itemize}
    \item \textit{server-only authentication}, in which only the server proves its identity (the ordinary web case);
    \item \textit{mutual authentication}, or \textit{mTLS}, in which the client proves its identity as well.
\end{itemize}

At the level of abstraction used throughout this work, a handshake proceeds as follows.
\begin{enumerate}
    \item The client sends a \textit{ClientHello} containing a fresh random value $cr$ and a Diffie-Hellman key share $g^{x}$, where $x$ is a fresh secret exponent.
    \item The server answers with a \textit{ServerHello} containing its own random value $sr$ and key share $g^{y}$. Both parties can now compute the shared secret $g^{xy}$, from which every later key is derived by hashing. Under a key derived from $g^{xy}$, the server then sends:
    \begin{itemize}
        \item its \textit{Certificate}, a binding of its name to its public key signed by a certification authority (CA);
        \item a \textit{CertificateVerify}, its signature over the transcript of everything sent so far;
        \item a \textit{Finished} message, a message authentication code over the transcript.
    \end{itemize}
    \item In mTLS, the client returns its own Certificate, CertificateVerify and Finished in the same way.
    \item Application data, which we call a \textit{request} and a \textit{response}, then travels under application traffic keys, also derived from $g^{xy}$.
\end{enumerate}

Our model makes the usual simplifications of a symbolic analysis:
\begin{itemize}
    \item only Diffie-Hellman key exchange is modeled (no pre-shared keys, resumption, 0-RTT or HelloRetryRequest);
    \item version and cipher suite negotiation is not modeled, so downgrade attacks are out of scope;
    \item a hash is a perfect one-way function, so transcript collisions are out of scope;
    \item the key schedule derives keys from the randoms and the shared secret rather than from the full transcript.
\end{itemize}

Our starting point was a CPSA model supplied by our mentor, \texttt{tls13\_final.scm}, together with a file of macros that build the TLS messages. Following Cremers et al. \cite{cremers2017tls13}, the model states its security properties as goals of three kinds:
\begin{itemize}
    \item \textit{Injective agreement}: whenever one party completes a run, there is a unique run of the other party that agrees with it on every value of the handshake.
    \item \textit{Key secrecy}: the adversary never learns the application traffic keys.
    \item \textit{Perfect forward secrecy} (PFS): data protected by a session's keys stays secret even if a party's long-term signing key is stolen \textit{after} the session has finished.
\end{itemize}

In CPSA, a secrecy goal is checked with a \textit{listener}, a strand that receives the secret from the network. The goal holds if no execution of the protocol can deliver the secret to the listener. Assumptions are expressed through two statements:
\begin{itemize}
    \item a \textit{non-originating} value (\texttt{non}) is one that never travels on the network, such as an uncompromised private key;
    \item a \textit{uniquely generated} value (\texttt{ugen}) is one created fresh by exactly one party, such as a Diffie-Hellman exponent.
\end{itemize}

With eight goals for each mode, we refer to the server-only goals as S1-S8 and to the mutual-authentication goals as M1-M8. They are listed in Table~\ref{tab:goals}. The server-only model documents that four of its goals (S2, S5, S6 and S8) fail by design. This is to be expected, as a server that never authenticates its client can conclude nothing about who it is talking to.

\subsection{Mutation Analysis as a Source of Ground Truth}
\label{subsec:mutation}
The second and third prongs are comparisons. To judge whether s(CASP) can reach the same conclusions as CPSA, or whether a learned automaton exhibits the same vulnerabilities as the protocol, we need questions whose answers we already know. Mutation analysis provides exactly this. We deliberately introduce a small fault into the protocol, predict its effect on every goal, and confirm the prediction with CPSA. Each confirmed mutation becomes a piece of ground truth.

\subsubsection{The First Round of Mutations}
In late September, each team member wrote mutations of the mentor's model:
\begin{itemize}
    \item \textbf{Andrew Bourinski}: deleting the server's CertificateVerify (m1), and removing the client's key share from the transcript the server signs (m2).
    \item \textbf{Aendri Singh}: deleting the Finished messages (m3), and removing the freshness of the Diffie-Hellman exponents (m4).
    \item \textbf{Pooya Zolfagharkhani}: extending the model to mutual authentication (m5), and deleting the client's signature (m6).
\end{itemize}
This first round taught us a great deal about CPSA, but it also showed that the results could not be compared with one another. Each mutation had been applied to its own separately edited copy of the model. One copy included a macro file that did not exist, one mutation edited a macro that the model never used, and another also deleted assumptions from the goals, which changes the question being asked rather than the protocol. We therefore rebuilt the study around a stricter method.

\subsubsection{Method}
The method rests on four rules.
\begin{enumerate}
    \item \textbf{Fixes and mutations are never mixed.} All corrections to the model go into a single \textit{baseline}. The baseline is frozen, with a manifest of cryptographic hashes, before any mutation is run.
    \item \textbf{Every mutation changes exactly one line.} A deleted message appears both on the wire and inside every transcript that a later signature or MAC covers, so a literal deletion touches many places. We therefore refactored the model so that every mutation point is a named macro whose baseline body is the original term. A script verifies that this refactoring changes nothing: CPSA's macro expansion of the refactored model is identical to that of the original. A mutation then redefines exactly one macro. A deletion is written as an empty term, which CPSA splices out of every message and transcript in which it occurred.
    \item \textbf{Predictions come first.} For every variant, we wrote down the predicted verdict for all sixteen goals, with a rationale, and sealed the predictions with a SHA-256 hash before the variant was run. A disagreement between prediction and result is reported as a finding; the prediction is never edited.
    \item \textbf{Parameters are fixed.} Every variant is run twice: once with a strand bound of 12 and a step limit of 500, and once with CPSA's defaults (a strand bound of 12 and a step limit of 2000). A goal on which the two runs disagree is flagged rather than averaged.
\end{enumerate}

A goal is recorded as:
\begin{itemize}
    \item \textit{HOLDS} if the search finished and every shape satisfies it;
    \item \textit{VIOLATED} if some shape contradicts it (a shape is a realized execution, so this is conclusive even if the search was later cut off);
    \item \textit{INCOMPLETE} if no counterexample was found but the search did not finish.
\end{itemize}

\subsubsection{Corrections to the Model}
Building the baseline required eight corrections, listed in Table~\ref{tab:fixes}. We classify each as a \textit{transcription error} (the model did not say what its authors evidently meant) or a \textit{modelling decision} (a choice about what is modeled, which could move a verdict and is therefore stated and justified).

Two corrections deserve explanation.
\begin{itemize}
    \item \textbf{F4} is a defect in the macro file itself: the macro that builds the transcript covered by the client's signature passed the two Diffie-Hellman exponents to an inner macro in the wrong order. Only the mutual-authentication path uses this macro, so the server-only results were unaffected. We reported the defect to our mentor, who has since corrected his copy.
    \item \textbf{F5} resolves the reason the early mutual-authentication runs never finished. Client and server certificates were the same term, so CPSA could explain a server certificate as having come from a client that presented it as its own, and then explain that client's certificate the same way, without end. A client certificate is now signed over a \texttt{"client"} tag. This models a real property: an X.509 certificate carries an extended key usage, and a server must not accept a certificate for client authentication unless it allows that use \cite{rfc5280}.
\end{itemize}

F7 and F8 were found by a separate investigation of a result that looked too good. On the first baseline, M8 held even in a variant in which the adversary could already read the session keys. Profiling CPSA's search showed that no client strand ever appeared in it. The client's first use of its signing key counted as \textit{generating} that key, which contradicted the uniqueness of the key-generation role, so no client could ever coexist with the key-disclosure machinery. The goal held vacuously. With F7 the client loads its key from storage, as real clients do. With that fixed, a second defect surfaced: M8 let the key leak before the server had checked the client's signature, which F8 corrects. After both fixes, M8 fails in the variant where it must fail, and that is the evidence that the fixes are right.

\subsection{The Mentor's Lemma-Based mTLS Models and Their Validation}
\label{subsec:lemmas}
After we sent these results to our mentor, he supplied three new models of the mutual-authentication protocol, built around an idea worth explaining. CPSA spends much of its effort on questions it can never answer positively, for instance how the adversary might obtain an honest party's Diffie-Hellman secret. A \textit{lemma} answers such a question once and for all. It is first proven as a goal, and then restated as a \textit{rule} that CPSA uses to prune every later search.

\begin{itemize}
    \item \texttt{mtls0.scm} proves that honest clients and servers never leak their Diffie-Hellman exponents.
    \item \texttt{mtls1.scm} adopts those lemmas as rules. It then proves that the shared secret $g^{xy}$ is never leaked when an honest party talks to a \textit{legitimate} counterpart, meaning one that follows the protocol and whose signing key is uncompromised.
    \item \texttt{mtls2.scm} adopts all four lemmas as rules. It then gives two starting scenarios, one from each side. Each yields a single shape in which client and server agree on every value, which demonstrates mutual authentication.
\end{itemize}
Our mentor also observed that the certification authority's key need not be assumed uncompromised; only the counterpart's signing key matters.

Because a rule that is not actually true can silently hide an attack, we validated these models independently before building on them. Every test model was the mentor's protocol, unchanged, with only rules removed or goals added. The 78 checks all produced the expected result, the slowest in about one second.
\begin{itemize}
    \item \textbf{Reproduction.} All three models give exactly the results described.
    \item \textbf{Soundness of the rules.} Each rule is applied to shorter strands than its lemma was proven for. For example, the client-exponent rule is used after the client's first event, but was proven only for clients that had completed four events. We re-proved every lemma at the length at which its rule is used, and all hold.
    \item \textbf{Mutual authentication as goals.} We restated the mentor's result as goals rather than as an inspected shape: full agreement on all nine handshake values from each side, together with \textit{injectivity}, meaning that the matching run of the other party is unique. All hold, and none needs the certification authority's key to be uncompromised.
    \item \textbf{Which key matters.} A server that assumes only the client's key is uncompromised authenticates the client. A server that assumes only its \textit{own} key does not. Legitimacy is therefore a property of the counterpart's key, as our mentor stated.
    \item \textbf{Negative controls.} Removing the counterpart-key assumption makes every positive result fail, so none of the proofs is vacuous.
    \item \textbf{Cross-check against our ground truth.} We applied mutations m1, m6 and m8 to the mentor's model and re-proved each lemma on each mutant before reusing it there. All thirty predictions, sealed in advance, were confirmed. The mentor's model and our baseline therefore agree on every mutual-authentication mutant they share.
\end{itemize}

Two findings went back to our mentor.
\begin{itemize}
    \item On our version of CPSA, the rules do not change the analysis at all: with them and without them, the skeleton counts are identical. With the old macro file, the analysis never finishes whether or not the rules are present, and with the corrected file it finishes either way. The speedup came from the F4 correction, and we have asked which CPSA version he uses.
    \item The session-key secrecy goals need a larger strand bound (30 instead of the default 12) to finish, which they then do in under a second.
\end{itemize}

\subsection{Resolving Forward Secrecy}
\label{subsec:pfs}
Goal M8 asks the following. An honest server completes a session, and the client's signing key is disclosed only afterwards; can the adversary read the server's response? On the unmodified model, CPSA never finished. We set out to find out why, and to give M8 an answer.

\paragraph{Diagnosis.} Profiling the search showed that the obstacle is not forward secrecy itself.
\begin{itemize}
    \item Following the mentor's technique, we proved eleven lemmas under M8's own assumptions: that the Diffie-Hellman value $g^{xy}$, both handshake keys, the master secret and both application keys of the session are unavailable to the adversary. All hold in about 1.5 seconds, and all fail on m6, so they discriminate.
    \item With all of them as rules, M8 still did not finish. The search grows while CPSA explains how the server came to receive the client's handshake message. Certificates travel only inside encrypted handshake messages, so every explanation of a certificate introduces another honest session, whose messages must themselves be explained.
\end{itemize}
None of the following made M8 finish: publishing certificates at key generation, separating client keys from server keys (an X.509 key-usage restriction), protecting the server's key, adding further lemmas, or changing CPSA's search order.

\paragraph{A pitfall.} Our fix F7 made each role begin with a key \textit{load}, and a client's load looks exactly like a server's. CPSA decides which role a strand belongs to by matching its sequence of events against the roles. A rule stated about the first event of a client therefore also matches every server. One of our early rules pruned \textit{every} execution as a result, so M8 appeared to hold even in m6, which we know to be broken. Rules in this protocol must therefore refer to at least the second event, where the roles first differ. The episode is a reminder of why we run a negative control for every positive result.

\paragraph{Decomposition.} Forward secrecy, like most proofs of it, rests on two properties:
\begin{enumerate}
    \item \textit{Authentication before compromise}: when the server receives the client's message, it is talking to a genuine client, and the client's key has not yet leaked.
    \item \textit{Secrecy given an authenticated session} (M8$'$): if client and server agree on every value and the client's key leaks afterwards, the response stays secret.
\end{enumerate}
Table~\ref{tab:m8} gives the evidence for each.

\begin{table}[h!]
\centering
\small
\begin{tabular}{|p{6.8cm}|p{3.8cm}|p{3.8cm}|}
\hline
\textbf{Property} & \textbf{Unmodified (m5)} & \textbf{m6} \\
\hline
M8$'$, checked by CPSA & No attack (0.1 s) & No attack \\
Authentication before compromise, in the PFS protocol & Did not finish & Attack found \\
The same property as M2, in the mTLS protocol & Holds & Violated \\
\hline
\end{tabular}
\caption{The two halves of M8.}
\label{tab:m8}
\end{table}

Two controls show that the result for M8$'$ is meaningful:
\begin{itemize}
    \item without the adversary's listener the scenario does occur, so ``no attack'' is not an empty statement;
    \item a listener placed on something that genuinely leaks, the disclosed key, is found.
\end{itemize}

The first property transfers from M2 by a short argument. Take any execution in which the client's key leaks after the session and cut it off before the leak. In what remains, the key has never been sent, so this is an execution of the mTLS protocol in which the key is uncompromised, and M2 applies.

We conclude that \textbf{M8 holds for the unmodified protocol, by decomposition, and is violated for m6}. The transfer argument is made on paper rather than checked by CPSA, and we have asked our mentor to review it.

\subsection{The Mentor's Final Model with the Tamarin Goals}
\label{subsec:mtlsfinal}
Our mentor has since supplied \texttt{mtls\_final.scm}, which states the security goals of the Tamarin analysis of TLS 1.3 \cite{cremers2017tls13, meier2013tamarin} for the mutually authenticated protocol. It contains:
\begin{itemize}
    \item the lemma-based mTLS protocol of Section~\ref{subsec:lemmas}, with goals for injective agreement from each side and for the secrecy of both application keys from each side;
    \item a forward-secrecy protocol with key storage, key generation and key disclosure, with two forward-secrecy goals. In both goals it is the \textit{server's} key that is disclosed after the handshake. Our mentor notes that disclosing the client's key instead would give the same results.
\end{itemize}

The file runs in about four seconds, and we checked it in the same way as the earlier models.
\begin{itemize}
    \item \textbf{The six mutual-authentication goals hold, non-vacuously}: both roles appear in their analyses, and the results agree with our own validation.
    \item \textbf{The client-view forward-secrecy goal holds only vacuously.} Its analysis never adds a server, although a client cannot finish without verifying a server's signature. The cause is the pitfall described above. In this protocol both roles begin with a key load, and the rule \texttt{clients-servers-distinct}, which says that no name acts both as a client and as the server of some client, mentions the client's first event. It therefore matches every server as well, and so it forbids a client from talking to any server that appears in the execution. We confirmed this in three ways:
    \begin{itemize}
        \item an ordinary, honest session has no shapes at all under the file's rules;
        \item it has shapes once that rule is removed;
        \item with the server's signature deleted (m1), the goal still ``holds'', which cannot be right.
    \end{itemize}
    Restating the rule so that it refers to the client's second event restores honest sessions, and m1 is then violated as it should be. The unmodified goal, however, then reaches our five-minute limit without a counterexample, much as M8 did.
    \item \textbf{The server-view forward-secrecy goal is violated.} The counterexample is not a failure of forward secrecy: the adversary obtains the \textit{client's} key before the session and impersonates the client. The goal places no constraint on the client's key, so the attack is legitimate for the goal as written. The goal needs the assumption that the client's key is uncompromised until the session ends; its comment, carried over from the server-only model, says that it cannot be satisfied.
\end{itemize}

These are questions for our mentor rather than conclusions, and we have reported them together with our resolution of M8. They also suggest that disclosing the client's key instead of the server's would not, in fact, give the same results. That is the case of M8, which CPSA could not decide in a single run.

\subsection{Machine Learning Assistance: Exploring ModelForge}
\label{subsec:modelforge}
The research plan promised to explore machine learning tools such as ModelForge in support of the first prong. ModelForge \cite{10.1007/978-3-031-87496-3_10}, of which our mentor is a co-author, translates a natural-language protocol specification into a CPSA protocol definition using a fine-tuned LLM, and a domain expert reviews the result. An earlier paper by the same group used Code Llama and reported a qualitative example \cite{duclos2024rfc2cpsa}. A 2026 thesis from Mississippi State University\footnote{\url{https://scholarsjunction.msstate.edu/td/6890}} evaluated fifteen LLMs on 104 protocols and found that 71--97\% of outputs were syntactically valid, and that curated reference examples help. We could not obtain the tool, its model or its benchmark, and we have asked our mentor for access.

In the meantime we reproduced the approach, and asked a stricter question than syntactic validity: are the \textit{verdicts} right?
\begin{itemize}
    \item \textbf{Specification.} We wrote a plain-English specification of mTLS 1.3 in the terms of RFC~8446, without CPSA vocabulary, in four versions matching our mutants: unmodified (m0), and without the server's, the client's, or both signatures (m1, m6, m8).
    \item \textbf{Interface.} A short contract fixes the names of the roles and variables, so that our goals can be attached automatically to whatever the model produces. It plays the part of ModelForge's structured output.
    \item \textbf{Translator.} Claude Sonnet 5.5 saw only the prompt, never our models or answers, and translated each version three times under each of two conditions:
    \begin{itemize}
        \item zero-shot;
        \item with two stock CPSA examples, neither of them TLS: the Station-to-Station protocol \cite{diffie1992sts} and a plain Diffie-Hellman exchange.
    \end{itemize}
    A model that CPSA rejected was given one chance to repair itself from CPSA's error message, mirroring ModelForge's post-processor.
    \item \textbf{Scoring.} Each generated model was checked against the same four goals evaluated on the mentor's validated model: authentication in each direction and the secrecy of the request and of the response. It also had to pass an \textit{executability} check, that each role can actually run to completion, because a model in which a role can never finish satisfies every goal vacuously.
\end{itemize}

Table~\ref{tab:modelforge} gives the results. With two reference examples, every generated model reached the correct verdict on every goal for every variant, in agreement with the thesis finding that reference examples help.

All three zero-shot failures had one cause. They are exactly the three models, of twenty-four, that wrote security assumptions (``my signing key is uncompromised'') into the definitions of the roles themselves. Such a model passes every syntactic check, yet CPSA could not analyze any of them within fifteen minutes.

This is the kind of error that motivates our concern with hallucination in Section~\ref{sec:mot}. It is plausible and well formed, and it is wrong in a way that only someone who understands the model will notice. It is why ModelForge's authors insist on expert review, and it suggests that ModelForge should be evaluated on the correctness of verdicts and not only on syntax. We were unable to compare several models, as the thesis did, because the command-line tool available to us truncated the output of the smaller model.

\subsection{A Benchmark with Four Kinds of Answer}
\label{subsec:benchmark}
The product of the first prong is a benchmark: a set of protocol variants whose behavior under each goal is known. The two unanswered cases of our mutation study turned out to be among its most useful members, because a benchmark that records only ``holds'' and ``violated'' cannot reward a tool for knowing the limits of what can be concluded. Every cell of the benchmark therefore records one of four answers:
\begin{itemize}
    \item \textit{HOLDS};
    \item \textit{VIOLATED};
    \item \textit{UNDECIDED}: CPSA's search does not finish, as with M8 on its own, whose resolved answer from Section~\ref{subsec:pfs} is recorded alongside;
    \item \textit{INEXPRESSIBLE}: CPSA rejects the model, as with m7.
\end{itemize}
The methods of the second and third prongs will be scored on whether they report the right kind of answer. A method that claims a verdict on m7, or claims an attack on one of the five equivalent mutants, must be able to justify it.

\subsection{Status and Next Steps}
\label{subsec:status}
The first prong is complete. Its products are:
\begin{itemize}
    \item a frozen, corrected and documented model of TLS 1.3 in both modes;
    \item a benchmark of twelve variants and sixteen goals with sealed predictions;
    \item an independent validation of our mentor's lemma-based models;
    \item a resolution of forward secrecy in the mutually authenticated protocol;
    \item an evaluation of ModelForge-style translation against verified ground truth.
\end{itemize}

Four questions remain open with our mentor:
\begin{itemize}
    \item whether the client tag on certificates is acceptable;
    \item whether the argument that completes the resolution of M8 is sound;
    \item the behavior of the forward-secrecy goals in \texttt{mtls\_final.scm};
    \item access to ModelForge.
\end{itemize}

For the second prong, CPSA can already export its analyses as Prolog terms. We will use these to encode the protocol's roles for s(CASP), write the adversary's capabilities as answer set rules, and pose each goal as a query, so that a model found by s(CASP) is an attack and its justification tree explains it. We will validate the encoding first on a protocol with a well-known attack, and then score it against the benchmark, beginning with the variants that discriminate and ending with the equivalent mutants, on which it must find nothing.

For the third prong, we will implement a small TLS 1.3 server, with one switch for each mutation, as the black box for the $L^{*}$ algorithm. We will learn a state machine for each variant, and then ask of each learned machine the same questions the benchmark asks of CPSA. Of particular interest are the equivalent mutants. CPSA's goals cannot tell them apart from the unmodified protocol, yet a server that no longer checks a Finished message may well behave differently as a state machine. This is precisely the kind of gap between formal verification and observed behavior that the third prong was proposed to find.
