# Specification

# TLS 1.3 handshake with mutual authentication (abstracted from RFC 8446)

Two principals run the protocol: a client and a server. A certification
authority (CA) has issued each of them a certificate. A certificate binds a
principal's name to that principal's public signature-verification key and is
signed by the CA.

Keys and values:
- Each principal has a long-term asymmetric key pair. The server's public key
  is `spk`; the client's public key is `cpk`. Each signs with the matching
  private key.
- The client chooses a fresh random value `cr` (client random) and a fresh
  Diffie-Hellman exponent `x`. The server chooses a fresh random value `sr`
  (server random) and a fresh Diffie-Hellman exponent `y`. `g` is the group
  generator. Exponents are never sent.

Message flow:

1. Client -> Server, in the clear: **ClientHello**, carrying `cr` and the
   client key share `g^x`.
2. Server -> Client: **ServerHello**, in the clear, carrying `sr` and the
   server key share `g^y`. In the same flight, encrypted under the *server
   handshake traffic key*:
   - **Certificate**: the server's name, its public key `spk`, and the CA's
     signature over that name and key.
   - **CertificateVerify**: the server's signature, made with its private
     key, over the transcript so far (ClientHello, ServerHello, server
     Certificate).
   - **Finished**: a MAC over the transcript so far (including the server
     CertificateVerify), keyed with a *finished key* derived from the server
     handshake traffic key.
3. Client -> Server, encrypted under the *client handshake traffic key*:
   - **Certificate**: the client's name, its public key `cpk`, and the CA's
     signature over that name and key.
   - **CertificateVerify**: the client's signature, made with its private
     key, over the transcript so far (everything in messages 1 and 2, plus
     the client Certificate).
   - **Finished**: a MAC over the transcript so far (including the client
     CertificateVerify), keyed with a finished key derived from the client
     handshake traffic key.
4. Client -> Server: a fresh application request `request`, encrypted under
   the *client application traffic key*.
5. Server -> Client: an application response `response`, encrypted under the
   *server application traffic key*.

Each receiver checks everything it can: it verifies signatures with the
public key in the received certificate, verifies the CA signature on the
certificate, verifies the Finished MAC, and decrypts with the keys it derived
itself.

Key schedule (simplified; keep it one-way):
- The shared Diffie-Hellman secret is `g^(xy)`. The client computes it from
  `g^y` and `x`, the server from `g^x` and `y`.
- The handshake secret is derived from the shared secret.
- The client and server handshake traffic keys are each derived from the
  handshake secret, a distinct label, and both randoms.
- A master secret is derived from the handshake secret.
- The client and server application traffic keys are each derived from a
  distinct label, both randoms, and the master secret.
- Model each derivation with a one-way hash. Distinct labels must give
  distinct keys.

Freshness and secrecy assumptions belong to the roles: the client's `x` and
the server's `y` are freshly generated by their owners.


## Variant

In this variant the client does **not** send a CertificateVerify message. Nothing in the handshake is signed with the client's private key. Every transcript that would have contained the client CertificateVerify is computed without it. Everything else is unchanged.
